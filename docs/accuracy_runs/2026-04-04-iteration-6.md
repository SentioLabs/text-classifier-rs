## What Changed (done in a parallel session)

### 1. Dual-LLM label audit

Extended `audit_model_errors.py` with `--dual-llm` flag for 4-way voting:
model prediction + current label + Haiku 4.5 + GPT-5.4-mini.

- 271 eval errors audited → 177 corrections applied, 4 garbage samples dropped
- 1,896 training corrections (1,826 auto + 70 GPT-5.4 tiebreaker for 2-2 ties)
- Added `--filter-subtypes` to scope training audit to weak sub-types

### 2. Architecture upgrade

| Parameter | Before | After |
|-----------|--------|-------|
| First hidden layer | 128 | 256 |
| Dropout | 0.3 | 0.15 |
| BatchNorm | No | Yes (before ReLU) |
| Sub-type loss weight | 0.3 | 0.5 |
| LR warmup | None | LinearLR, 10 epochs |

New CLI flags in `train.py`: `--dropout`, `--hidden-dim`, `--sub-type-weight`,
`--no-batchnorm`, `--warmup-epochs`.

### 3. Eval/training Parquet support

`eval_onnx.py` now accepts `.parquet` files alongside JSONL, enabling model
predictions on training data for label auditing.

### Weakest sub-types
| Sub-type | Issue |
|----------|-------|
| `unknown` | ~50% accuracy (inherently ambiguous, 67 samples) |
| `plain` | ~85-90% (giant catch-all bucket, biggest error source) |
| `json/jsonl` | ~80-87% (JSON with prose content vs prose with JSON) |
| `ini` | ~90% (config files confused with code) |

### Root causes of remaining errors
1. **Genuinely ambiguous content** — text that reasonable humans would disagree on (audit logs that are both structured and prose-like, medical forms, financial reports)
2. **The `plain` bucket problem** — after remapping ghost sub-types, `plain` became a ~1,275-sample catch-all. Many of these are actually structured data in plain-text format (key-value, tabular) that Magika couldn't identify as a specific format
3. **Diminishing returns on label correction** — each round of LLM voting fixes some labels but also makes some previously-correct labels worse. We're approaching the noise floor of automated labeling

## Path to 97%

### Option A: Better sub-type assignment for `plain`
The `plain` sub-type is too coarse. Many `plain/structured` errors are actually `key_value`, `log_lines`, or `fixed_width` that Magika couldn't detect. A second-pass feature-based sub-type refinement (using our own features, not Magika) could reclassify these:
- If `key_value_ratio > 0.5` and `sub_type == plain` → reclassify to `key_value`
- If `log_line_ratio > 0.3` and `sub_type == plain` → reclassify to `log_lines`
- If `delimiter_consistency > 0.6` and `sub_type == plain` → reclassify to `csv` or `tsv`

### Option B: Remove `unknown` sub-type samples
The 67 `unknown` samples at 50% accuracy are pure noise. Removing them from eval (and training) would immediately boost accuracy by ~0.8 points and give the model cleaner signal.

### Option C: Manual curation of top error samples
Review the top 50-100 remaining errors by hand. Many of the prose→structured errors are audit logs, medical records, and financial forms that ARE structured despite being plain text. Manual labels would establish ground truth for these boundary cases.

### Option D: Multi-label classification (epic feathierar-16wj.03j58p)
Instead of forcing a single category, allow documents to be tagged with features like `has_code`, `contains_prose`, `has_tables`. This sidesteps the forced-choice problem for genuinely mixed content.
