## Two Dominant Failure Modes

### 1. Structured over-prediction (code → structured, artifact → structured)

The model now over-classifies as structured. This affects:
- **Code sub-types** with config-like syntax: YAML (48 misses), INI (24), TOML (20)
- **Artifact sub-types** with tabular remnants: pdf_dump (52 misses), boilerplate (37), skip (20)

Root cause: Real config files from The Stack share syntactic patterns with code (indentation, brackets, key-value pairs) and with extracted documents (tabular layouts, form fields). The 28-feature set doesn't have enough signal to disambiguate these reliably.

### 2. Artifact under-detection (artifact → prose, artifact → code)

The model still misses artifact samples that look "readable":
- `ocr_garbage` → prose (34 misses): OCR output with enough real words to look like prose
- `boilerplate` → prose (21): License text is grammatically correct English
- `boilerplate` → code (19): License files from code repos contain code-like patterns

## Critical Finding: Eval Set Instability

The `train:split` step regenerates `eval/clear.jsonl` from the full data pool on every run. Adding new real-world data sources changes the eval set composition, making iteration-over-iteration comparison unreliable.

**Recommendation**: Freeze the current `eval/clear.jsonl` and `eval/boundary.jsonl` as the permanent benchmark. All future iterations should compare against this fixed eval set. The current eval is the most realistic we've had — it contains genuine PDF extractions, real license files, and real config files from production codebases.

## Next-Iteration Hypotheses

### Hypothesis 1: Freeze eval, retrain, measure true delta

Freeze eval sets, then retrain with the same data. This establishes a true baseline on the realistic eval set before making further changes.

### Hypothesis 2: Address code↔structured confusion with code-specific features

The YAML/INI/TOML confusion suggests the model needs features that distinguish "configuration syntax" from "programming syntax" — e.g., function definition density, import/require patterns, control flow keywords, or indentation-as-semantics ratio.

### Hypothesis 3: Address artifact→structured with harder negatives

The pdf_dump→structured pattern (52 misses) suggests the model sees tabular remnants in extracted PDFs and classifies them as structured data. Training with hard negatives — extracted documents containing tables that should still be classified as artifact — would help.

### Hypothesis 4: Reduce structured training volume

The structured category may be over-represented relative to its eval share. With 24K training samples producing 94.4% recall but dragging code down to 87.7%, reducing structured training volume or increasing code volume may rebalance without losing structured gains.
